# Toolchain

Every version here is pinned. `scripts/setup.sh` verifies each one and fails loudly on a mismatch —
it will not silently accept a newer release. Determinism is the product: two runs of the same
scenario must produce identical results to the microsecond, and that only holds if the stack under
them does not move.

| Component | Pinned version | Why this version |
|---|---|---|
| Renode | `1.16.1` | Executes real ARM binaries, models peripherals, and supports multiple machines on one shared CAN hub. Pinned because peripheral model behaviour and monitor command surface change between releases, and a changed peripheral model silently changes measured latencies. |
| Zephyr RTOS | `v3.5.0` | Machine-readable hardware description, and the generation Renode's own CAN test suite is built against. **Newer Zephyr's init aborts on some emulated platforms**, with an obscure failure mode. Do not upgrade without a green run. |
| Zephyr SDK | `0.16.8` | The SDK release matched to Zephyr v3.5.0. Provides `arm-zephyr-eabi`. |
| Python | `3.x` + `pyyaml` | The test engine has exactly one dependency so it runs anywhere with no install friction. |
| IronPython | `2` (embedded in Renode) | `harness/can_toolkit.py` is loaded into Renode's monitor, not run host-side. Python 2 statement syntax (`print 'x'`), and non-ASCII must be transliterated before it reaches the interpreter. |
| Robot Framework | latest | Renode's native test integration. Suites are generated by the harness, never hand-written. |
| Node | 20+ | Astro 5 + React 19 for the Studio. |

## Where it installs

The toolchain is installed **rootless**, entirely under `$HOME`. Nothing requires `sudo`:

| Component | Location |
|---|---|
| Renode (portable build) | `$HOME/bench-tools/renode-1.16.1/` |
| Zephyr SDK | `$HOME/zephyr-sdk-0.16.8/` |
| Zephyr workspace (west) | `$HOME/zephyrproject/` |
| Python tooling | `$HOME/bench-venv/` |

Renode's portable Linux tarball bundles its own runtime, so no system Mono or .NET package is
needed. The Zephyr SDK registers itself as a CMake package under `$HOME/.cmake`, which is how
`west build` finds `arm-zephyr-eabi` without touching `/opt` or `/usr`.

## Platform notes

The reference environment is **Linux x86-64**. On Windows, the toolchain runs under **WSL2**; the
Zephyr SDK and Renode do not have first-class native Windows support for this workflow, and
`scripts/setup.sh` and `scripts/boot-check.sh` are POSIX shell. Drive the build from a WSL shell
with the repository checked out on either filesystem — note that building on `/mnt/c` is
substantially slower than on the WSL filesystem, because of the 9p filesystem bridge.

`dtc` (device-tree-compiler) is **not** required. Zephyr parses devicetree with its own Python
`edtlib`; `dtc` is only used as an optional validator and the build skips it when absent.

## Parallelism, measured on the target machine

`scripts/bench-parallelism.sh` runs the same tests at several worker counts and
reports wall clock and per-test time. Measured here, on 12 cores:

| workers | wall clock | per test | gain vs previous |
|---|---|---|---|
| 1 | 327.8 s | 36.4 s | — |
| 2 | 179.5 s | 19.9 s | +45% |
| 4 | **145.6 s** | 16.2 s | +19% |
| 8 | 148.7 s | 16.5 s | **−2%** |

**Ceiling: 4 workers.** Past that the wall clock stops improving and slightly
regresses — the tests are competing for the same cores rather than the suite
getting slower. That matches the shape of the workload: a multi-node test keeps
roughly three cores genuinely busy, because the emulated machines step through
virtual time in lockstep and are not all active at once. Guessing from `nproc`
would have suggested 12 and lost time.

`export BENCH_WORKERS=4`, or let `harness/run_suite.py` derive it from the core
count, which lands on the same number here.

Re-measure on a different machine before trusting the default: this is the one
number in the toolchain that is a property of the host rather than of the pinned
versions.

### A correction worth keeping

The first version of `bench-parallelism.sh` recommended **8** from this same
data. It compared each level's per-test time against the *single-worker* figure
and stopped when it rose 15% above it — but the N=1 run also carries the one-off
expansion cost, so its per-test time is inflated and every later level looks flat
against it. A plausible answer from the wrong comparison.

It now compares each level with the one below it, which removes the baseline
entirely: while there is spare capacity, adding workers shortens the wall clock
markedly; once the machine is saturated the curve flattens and reverses. The last
level that still bought a real improvement is the ceiling.
